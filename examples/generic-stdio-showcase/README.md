# Generic stdio MCP showcase

A small, runnable example of dagr-mcp's stdio connector governing a
**generic, third-party, unmodified MCP server** launched as a child process
over stdio -- in this case the official
[`@modelcontextprotocol/server-filesystem`](https://www.npmjs.com/package/@modelcontextprotocol/server-filesystem)
reference server.

## What this proves

Running `live_run.py` demonstrates **one configured governed path** through
`dagr_mcp_service`'s `StdioToolConnector` / `execute_governed_call`, over the
real filesystem MCP server, with no mocks or stubs:

- **1 admit**: a read call inside the configured allowed root is admitted;
  the child process runs and returns real file content.
- **3 refuse**, each with the child process spawned **zero times**
  (verified by sentinel file checks, not just by the returned decision):
  - a mutating call (`write_file`) inside the allowed root, refused by this
    example's policy, which admits reads only;
  - a read call outside the configured allowed root, refused by dagr-mcp's
    own path-containment check (not merely by the child server's own
    `--allowed-root` flag);
  - a tool name (`delete_everything`) that is not in the connector's own
    `known_tools` allowlist at all -- refused fail-closed by the connector
    itself, before any policy resolver runs and before any admission receipt
    is emitted.

`verify_receipts.py` then independently verifies every receipt emitted by
the run above, using the separately-installed `arcs-verify` package in a
fresh interpreter process that never imports any dagr-mcp producer module
(checked explicitly and reported in the output). It also mutates one signed
field per receipt and confirms `arcs-verify` rejects the tampered copy as a
signature failure.

**What this does *not* claim:** this example does not demonstrate that "the
filesystem is governed," nor any aggregate trusted / safe / compliant /
verified / governed verdict about the target server or about dagr-mcp as a
system. It demonstrates that this one admission/refusal decision, for these
four specific calls, against this one target server, under this one
configured policy, was made before child execution and is independently
checkable after the fact.

## Bypass limitation (read this before drawing conclusions)

`bypass_check.py` launches the identical filesystem MCP server directly
with the official `mcp` SDK client -- with **no dagr-mcp connector,
adapter, or policy in the loop at all** -- and performs the same class of
write that the governed run above refused. That write succeeds.

This is expected, and it is the point: **dagr-mcp's connector is a
configured binding that an operator chooses to place in front of a call
path, not an unbypassable perimeter around the target server's binary.**
Anything that can invoke the target server directly (a different caller, a
misconfigured deployment, a process that skips the connector) is
ungoverned by this example's policy. Governance guarantees here apply only
to calls that are actually routed through the configured
`StdioToolConnector` / `execute_governed_call` path.

## Prerequisites

- Python >= 3.11
- [`uv`](https://docs.astral.sh/uv/) (or `pip` + `venv`) to create an
  isolated environment
- Node.js and `npx` on `PATH` (used to launch the real
  `@modelcontextprotocol/server-filesystem` package via `npx -y ...`; no
  global npm install required)
- A local checkout of this `dagr-mcp` repository, installed into your
  environment (editable install, or a path passed via `--dagr-mcp-path` /
  the `DAGR_MCP_PATH` environment variable)
- A real, separately-installed `arcs-verify`
  (https://github.com/thelaplage/arcs-verify) for the independent
  verification step -- this example does not vendor or fake a verifier

## Run

From a clean checkout of this repo:

```bash
# 1. Isolated environment
uv venv /tmp/dagr-mcp-showcase-venv
source /tmp/dagr-mcp-showcase-venv/bin/activate

# 2. Install dagr-mcp (with the official MCP SDK extra, for bypass_check.py)
uv pip install -e ".[official-sdk]"

# 3. Install the independent verifier from its own repo
git clone https://github.com/thelaplage/arcs-verify /tmp/arcs-verify-src
uv pip install -e /tmp/arcs-verify-src

# 4. Shared workdir for this run's generated receipts/output (never commit it)
export DAGR_MCP_SHOWCASE_WORKDIR="$(mktemp -d)"

cd examples/generic-stdio-showcase

# 5. Optional: see what tools the target server actually advertises
python discover_full.py

# 6. The governed run: 1 admit + 3 refuse, receipts written to $DAGR_MCP_SHOWCASE_WORKDIR
python live_run.py

# 7. Independent verification of those receipts, in a fresh interpreter process
python verify_receipts.py

# 8. The bypass limitation: the same write, with zero dagr-mcp in the loop
python bypass_check.py
```

Nothing generated by these scripts (receipts, the trust bundle, allowed/
outside root scratch content, logs, or JSON output files) is meant to be
committed -- see the example-local `.gitignore`. Signing keys used by
`live_run.py` are generated at runtime by `SigningIdentity.generate(...)`;
none are baked into any committed file.

## Files

- `discover_full.py` -- lists the tools the real filesystem MCP server
  advertises, via dagr-mcp's `discover_tools()` helper.
- `live_run.py` -- the governed run: 1 admit + 3 refuse against the real
  server, with sentinel checks proving zero child executions for the
  refused calls, and signed receipts written to the workdir.
- `verify_receipts.py` -- independently re-verifies those receipts with a
  separately-installed `arcs-verify`, including a signed-field tamper
  check, from a process that imports no dagr-mcp producer module.
- `bypass_check.py` -- the same write, performed directly against the
  target server with no dagr-mcp connector in the loop, to make the bypass
  limitation concrete.
